## P0（2 条，必须立刻修）

### P0-1 `system:file:remove` 是死权限码，「删他人文件」能力不可达

- **现象**：代码里定义并消费了 `system:file:remove`，但权限清单里没有这一条 → 角色编辑器（树形勾选）根本列不出它，任何角色都拿不到该码 → `assertCanWrite` 的管理员分支永远走不到。
- **证据**：
  - `server/src/modules/file/file.constants.ts:24` —— `REMOVE: 'system:file:remove'`
  - `server/src/modules/file/file.service.ts:492` —— `if (matchPermission(user.permissions, 'system:file:remove')) return;`
  - `sys_permission` 实测 40 条中**无** `system:file:remove`（只有 `system:file:list`）
  - 采集机制：`server/src/common/authz/permission-catalog.ts` 只反射 `@RequiresPermissions`；而 `server/src/modules/file/file.controller.ts` 的删除路由**故意没挂**权限码（决策 ⑥：删除自己的文件不该被权限码挡住）
  - 后果：非上传人删除他人文件 → `file.service.ts:493` 直接抛 403
- **影响**：功能与设计意图不一致。要么该能力该有（管理员应能删任意文件），要么不该有（那就该删常量）。
- **改法（二选一，需拍板）**：
  - **A（推荐）**：删除 `file.constants.ts:24` 常量与 `file.service.ts:492` 判定，删除权限判定改为「仅上传人可删」；同步修 `docs/文件与附件.md` 第 6 节第 17 行。
  - **B**：保留管理员能力 → 在 `permission-catalog.ts` 的 `EXTRA_PERMISSIONS`（第 63 行）登记 `system:file:remove`，跑 `pnpm authz:sync` 入清单，并给删除路由补 `@RequiresPermissions`（但这会挡住「删自己传错的文件」，与决策 ⑥ 冲突，需一并调整）。

### P0-2 全局限流按 IP 计数，且未配 `trust proxy` → 全校共享一个配额

- **现象**：`ThrottlerGuard` 全局启用，默认 300 次/分钟，键为 `req.ip`。nginx 反代后 Express 拿到的 `req.ip` 是反代地址（`127.0.0.1`），**全校所有用户共用一个计数器**。登录日志、审计日志的 `ip` 字段同样失真。
- **证据**：
  - `server/src/app.module.ts:61` —— `ThrottlerModule.forRoot([{ ttl: 60_000, limit: 300 }])`
  - `server/src/app.module.ts:84` —— `{ provide: APP_GUARD, useClass: ThrottlerGuard }`
  - `node_modules/@nestjs/throttler/dist/throttler.guard.js:151` —— `normalizeIp(req.ip, ...)`
  - 全仓 `grep -rn "trust proxy|trustProxy" server/src/` → **零命中**；`server/src/setup-app.ts` 也没有 `app.set('trust proxy', ...)`
  - nginx 确实传了 XFF：`deploy/nginx/csmu-safecampus-admin.conf:81-82`（`X-Real-IP` / `X-Forwarded-For`），但 Express 不信任它
  - IP 消费点：`server/src/common/interceptors/audit.interceptor.ts:75`（`ip: req.ip`）、`server/src/modules/auth/auth.service.ts:126-127`
- **影响**：① 正常业务高峰会把全校打成 429；② 审计与登录日志的 IP 不可信，无法追责。
- **改法**：
  1. `server/src/setup-app.ts` 增 `app.set('trust proxy', 1)`（只信任一层 nginx，符合当前拓扑；多级反代再调）。
  2. 登录/验证码接口单独收紧：`@Throttle({ default: { limit: 5, ttl: 60_000 } })`（现为全局 300，撞库成本过低）。
  3. 登录日志 IP 改用 `X-Real-IP` 优先（`req.headers['x-real-ip']`），不依赖 `req.ip`。

### P1-2 生产环境 `JWT_SECRET` 有弱默认值

### P1-7 `dept` 移动时祖先前缀误匹配兄弟子树

- **现象**：移动部门时更新子孙 `ancestors`，用的 `LIKE '${oldPrefix}%'` 会把**兄弟子树**一起改掉（`oldPrefix` 如 `0,1` 会匹配 `0,10`）。
- **证据**：`server/src/modules/dept/dept.service.ts:127` —— `.where('d.ancestors LIKE :p', { p: `${oldPrefix}%` })`
- **对照（正确写法就在同项目里）**：`server/src/modules/menu/menu.service.ts:177-179` —— `.where('(m.ancestors = :p OR m.ancestors LIKE :pc)', { p: oldPrefix, pc: `${oldPrefix},%` })`
- **影响**：部门树结构被破坏 → 数据范围（`DEPT_AND_CHILD` 按 `ancestors` 求子树）随之失效 → **越权可见**。这是 P1 里最实质的一条。
- **改法**：把 `dept.service.ts:127` 改成 menu 的同款写法（精确等值 + `,` 边界通配）。

### P1-8 无任何改密 / 重置密码入口

- **证据**：`server/src/modules/user/dto/user.dto.ts:30` —— `updateUserSchema = updateSchemaOf(createUserSchema.omit({ password: true }))`，**没有**独立的改密 DTO/接口
- **影响**：初始密码 `Admin@12345` / `Demo@12345` 永远可用；用户泄露后无法自助改密。
- **改法**：新增 `PUT /user/:id/password`（需旧密码或管理员重置）+ 自助 `PUT /user/password`；审计 + 改密后 `session.invalidate`。

### P1-9 `sys_idempotency` 无过期清理任务

- **现象**：表有 `expire_at` 字段和 `idx_idem_expire` 索引，但**没有任何 cron 消费它**。
- **证据**：
  - 字段与索引：`server/src/modules/idempotency/entities/idempotency-record.entity.ts:16,35-36`
  - 全仓 cron 只有两个：`server/src/modules/file/file.cleanup.task.ts:25`（file-cleanup）、`server/src/modules/user/authorization.task.ts:28`（authz-revoke-expired）
  - 实测库内 `sys_idempotency` **177 行，全部 `status=done`**，最早 2026-10-29
- **影响**：只增不减，长期运行后单表膨胀；且过期记录若被 acquire 命中会返回陈旧结果。
- **改法**：新增 `@Cron(EVERY_HOUR)` 清理任务：`DELETE FROM sys_idempotency WHERE expire_at < NOW()`（与 file-cleanup 同模式）。

### P1-10 `sys_outbox` 无归档清理

- **证据**：`server/src/modules/outbox/entities/outbox-event.entity.ts` 有 `status: pending|processing|sent|failed` 与 `idx_outbox_status_available` 索引，但 grep 全仓**无任何 delete/purge/cleanup**；实测库内 37 行全 `sent`
- **改法**：加清理 cron，删 `sent` 且 `sent_at < NOW() - INTERVAL 7 DAY` 的行；`failed` 且超重试上限的行需告警而非静默留。

### P1-11 幂等冲突时无上限递归

- **证据**：`server/src/modules/idempotency/idempotency.service.ts:39-43` —— 查不到记录时 `return this.acquire(key, requestHash, ttlSeconds);`，**无深度上限**
- **触发条件**：并发插入 + 记录在两次查询之间被删（清理任务上线后概率上升）
- **影响**：栈溢出（`RangeError: Maximum call stack size exceeded`），请求 500
- **改法**：改为有限重试（如最多 3 次，每次加微小延迟），仍失败则抛 409/503。

### P1-12审计失败静默、契约未声明；不要求事务一致性，但要求「失败可见 + 边界写清」
现象：审计写入走进程内 EventEmitter，不随业务事务、不 await、落库失败仅记日志不告警。这不是要改成事务内同步审计的理由（中小系统"审计最终一致"是行业普遍取舍），真正的问题是：①失败被静默吞掉，运维和派生项目都感知不到；②"最终一致"这个隐含假设没有写进任何文档，派生项目会默认"底座保证审计落库"，等到合规检查才发现，返工成本高。

证据：

server/src/modules/audit/audit.service.ts:
34
 —— this.events.emit(AUDIT_WRITE_EVENT, entry
)
（只投递不 await）

server/src/modules/audit/audit.listener.ts:27-31 —— @OnEvent(..., { async: true })；:44-49 persist 失败仅 logger.error，不抛出、无死信、无指标

docs/整体方案与选型.md 全文无"审计最终一致 / 崩溃可能丢失"的边界说明

影响：

失败不可见：落库失败业务照常成功，审计静默缺失——这是真问题，且没有任何告警能发现；
契约未声明：派生项目（教育/政务/等保场景）会假设"底座保证了审计落库"，无法自行判断是否需要加固；
业务回滚/进程崩溃时审计与事实不一致——已知且可接受，但要写清，不能留给使用方猜。
改法（三件低成本事，不重构架构）：

失败可见：audit.listener.ts 落库失败时，除 logger.error 外写入死信（sys_audit_log 一条 status=failed 或独立死信表），并打一个可被监控抓取的 error 级别日志/指标。目标：任何一条审计没落库，运维能发现。
契约显式化：在 docs/整体方案与选型.md 增加一节，明确写「审计为最终一致：不随业务事务，进程崩溃/容器被杀时在途审计可能丢失；强合规场景请开启同步模式或自行改为事务内写入」。把隐含假设变成派生项目可据此决策的契约。
可选同步开关：配置项 AUDIT_SYNC（默认 false）。为 true 时 audit.service 改为事务提交后同步 await 落库（失败则告警/阻断可配）。底座默认异步保持性能，派生项目按合规等级自行开启——这是通用底座该有的弹性，改动局限在 audit 模块内。
不做的事（明确边界，避免误改）：不把审计并入每个业务事务、不做全局强一致改造。那会拖慢所有接口，且超出通用底座职责。本条的验收标准是"失败可被观测 + 边界已声明 + 需要时有开关"，不是"审计绝不丢失"。

定级说明：默认 P2（可靠性/契约，建议本轮修）。若该底座的目标客户明确要求等保三级/行业强审计，本条升 P1，且改法 3（AUDIT_SYNC 同步模式）从"可选"变为"必做"。

## P2（16 条，建议本轮修）

### P2-1 登录 / 验证码接口无限流

- **证据**：`server/src/modules/auth/auth.controller.ts:41`（captcha）、`:50`（login）均 `@Public()`，未加 `@Throttle`；全局默认 300/分钟（`app.module.ts:61`）
- **改法**：`@Throttle({ default: { limit: 5, ttl: 60_000 } })` 加在 login 上；captcha 10/分钟。

### P2-2 `CAPTCHA_ENABLED` 默认关闭，且前后端无一致性校验机制

- **证据**：`server/src/core/config/configuration.ts:17` —— `captchaEnabled: process.env.CAPTCHA_ENABLED === 'true'`（默认 false）；三份 `.env`（dev/prod/test）均 `CAPTCHA_ENABLED=false`；`server/src/modules/auth/auth.service.ts:65` 仅在开启时才校验验证码
- **前端**：`web_admin/src/views/LoginView.vue:15`、`web/src/views/LoginView.vue:13` —— `import.meta.env.VITE_CAPTCHA_ENABLED === 'true'`；`web_admin/` 与 `web/` **均无任何 `.env*` 文件**（只有 README 记录该变量）→ 构建期未注入则恒为 false
- **改法**：① captcha 默认改 `true`（`configuration.ts:17` 用 `!== 'false'`）；② 派生清单 `docs/init.md` 增加「前后端两处开关必须同时设置」条目；③ 启动时校验两者一致并 warn。

### P2-3 `TransformInterceptor` 的启发式判断会漏包装

- **证据**：`server/src/common/interceptors/transform.interceptor.ts:45` —— `if (keep || data?.code !== undefined) return data;`
- **影响**：任何返回体顶层自带 `code` 字段的业务对象都会被误判为「已包装」而跳过包装 → 前端拿到 `{code, msg?}` 缺 `data`。
- **改法**：改用显式标记（`@Keep()` / `@Raw()`）替代 `data?.code !== undefined` 的鸭子类型判断。

### P2-4 幂等与 Transform 的内外层关系靠 provider 声明顺序隐式决定

- **证据**：`server/src/common.module.ts` provider 顺序（TraceId → Audit → Idempotency → Transform），`server/src/common/interceptors/idempotency.interceptor.ts:35-36` 注释「必须位于 TransformInterceptor 之上（更外层）」
- **实测结论**：已用最小用例验证 Nest 的 `APP_INTERCEPTOR` 声明顺序 = 外→内（A-before → B-before → handler → B-after → A-after），**当前行为正确**
- **风险**：改顺序会静默破坏幂等回放（回放体被二次包装），且无测试守护

## 补充发现（修复第一批时新增）

> 2026-11-13 动第一批修复时又撞出来 4 条。**N-2 是本次最严重的一条**（比原 P0 更直接）。

### N-1（已修）`new HttpException('msg', 状态码)` 的 `body.code` 丢成 `500`

- **现象**：HTTP 状态码对（429 / 403），但响应体 `code` 是 `500`。前端按 `body.code` 判就会把限流/禁止访问误报成「服务器错误」。
- **根因**：`HttpException.getResponse()` 在**字符串构造**时返回裸字符串；内置异常（`NotFoundException` 等）走 `createBody()` 生成对象。全局过滤器只在「对象分支」回写了 `code`，字符串分支忘了 → 沿用初值 500。
- **触发面**：任何 `new HttpException('msg', 非500)` —— 最典型的就是 `ThrottlerException`（正是 P0-2 要修的限流）。
- **证据**：`server/src/common/filters/all-exception.filter.ts`（字符串分支无 `code = status`）；实测 `POST /auth/login` 第 6 次 → `HTTP 429 + {"code":500}`。
- **改法（已落地）**：字符串分支补 `code = status` / `data = res`；回归单测 `server/test/unit/exception-filter.spec.ts`（4 条）。

### N-2（已按 A 修复）演示数据迁移会创建 4 个**公开密码**账号

- **现象**：`1767000008000-SeedHazardDemo` 不只有演示单据，还会 `INSERT` 4 个可登录账号（`operator_bw` / `manager_bw` / `manager_xx` / `auditor_school`），密码统一 `Demo@12345`，**明文写在迁移源码里并随 SVN 分发**。任何一次 fresh 部署（含生产）都会得到这 4 个账号。
- **证据**：`server/src/core/database/migrations/1767000008000-SeedHazardDemo.ts:3-5`（`DEMO_PASSWORD_HASH` + 注释「生产上线前必须删除本迁移」）、`:13-18`（演示账号清单）；实测 `SELECT username FROM sys_user` → 4 个 `_bw`/`_xx`/`auditor_` 账号全在，`status=1`。
- **加剧因素**：`docs/部署端环境.md` 原先写「**没有任何账号**（连超管都没有）」—— **与事实相反**。已修正为醒目警告。
- **影响面**：它们无 `console:access`（进不了后台 8080），但能登录 8084 前端、能调 `/api/v1/*`（业务操作员权限）。对「等保 / 教育行业备案」场景是直接的扣分项。
- **改法（三选一，需拍板）**：
  - **A（已采用）**：该迁移 `up()` 开头加 `if (process.env.NODE_ENV === 'prod') return;` —— 已跑过的库不受影响（TypeORM 不会再跑），新库不再生成演示账号。
  - **B**：把演示数据从迁移里抽成独立脚本 `pnpm seed:demo`（仅 dev/test 手动跑），迁移保留纯结构 + 内置角色。改动大但最干净。
  - **C**：不动迁移，只在部署清单里加一条「上线后必须禁用这 4 个账号」。最省事但依赖人工不忘。
- **实测验证（已做）**：新建 `safe_campus_prod` 跑完全部迁移 → `sys_user` 0 行、`sys_dept` 0 行，`SeedHazardDemo` 在 `migrations` 表里记为已执行（不会重跑）。dev / test 行为不变。

### N-3（已修）e2e 被新限流打成随机失败

- **现象**：加上登录限流后，e2e 出现 `expected 200 "OK", got 429`（`test/authz.e2e-spec.ts` 等），且分布随机 —— 看起来像「测试不稳定」。
- **根因**：每个用例都要先登录拿 token，全来自同一个 `127.0.0.1` → 5/分钟的限流必然被打满。
- **改法（已落地）**：新增 `THROTTLE_ENABLED` 开关（`configuration.ts` → `AppThrottlerGuard.shouldSkip`），`.env.test` 设 `false`。用 env 显式关闭而不是硬编码 `NODE_ENV==='test'`，派生项目想测限流时可自行打开。

### N-4（已修）限流异常消息是英文框架串

- **现象**：超限返回 `ThrottlerException: Too Many Requests`（英文 + 框架内部类名）直接给终端用户看。
- **改法（已落地）**：新增 `server/src/common/guards/throttler.guard.ts`（`ThrottlerGuard` 子类），改抛中文「请求过于频繁，请稍后再试」，**保留 HTTP 429**（标准语义，便于 Nginx / 浏览器 / 监控识别）；配合 N-1 的修复，`body.code` 也正确为 429。

### N-5（已修 · P0 级运行保障）Redis 客户端不关连接 → 进程永不退出，`csmu.sh prod start` 卡死

- **发现场景**：验证 `authz:sync` 是否真的把新权限码写进 prod 库时，命令跑完打印了结果却**不退出**（`timeout 180` 被打了 124）。
- **根因**：`RedisModule` 用 `useFactory` 造 ioredis 客户端，全仓**无 `onModuleDestroy` / `quit()` / `disconnect()`**。ioredis 的 socket 是活跃 handle，`app.close()` 不管它 → Node 事件循环不空 → 进程不退。（`@nestjs/terminus` 的 DB 连接走 TypeORM，会被正常关闭，所以以前没暴露。）
- **影响（两层，第二层是部署级事故）**：
  1. `deploy/csmu.sh:261` 以 **无 timeout 的前台命令**跑 `node dist/scripts/authz-sync.js` → **`csmu.sh prod start` 永远停在「[4/6] 同步权限清单」**。因为写成 `|| warn`，它既不报错也不继续，看起来就像“部署卡住了”。
  2. `main.ts` 的 `app.enableShutdownHooks()` 名存实亡：SIGTERM 后进程不自己退，只能等 PM2 `kill_timeout` 到点发 SIGKILL —— 所谓「优雅停机」从未优雅过。
- **改法（已落地）**：`RedisService implements OnModuleDestroy` → `quit()`（发完在途命令再关，幂等键/防重锁这类写入不会被静默丢弃）+ 2s 兜底 `disconnect()`（Redis 不可达时 `quit()` 可能一直等）。
- **实测**：`node dist/scripts/authz-sync.js` 由「永不退出」→ **1.6s 退出，exit 0**；dev 服务 SIGTERM → **0.106s 退出**。回归单测 `server/test/unit/redis.service.spec.ts`（3 条）。
- **教训（已写进 `docs/坑与约束.md`）**：新增任何**外部连接**（Redis / 存储 / 定时器 / 子进程）都要问一句「谁在退出时关它」。
