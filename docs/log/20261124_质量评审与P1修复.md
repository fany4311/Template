## 3. 本轮修复

### P1-1 软删 + 单列唯一互撞（已修）

- 现象：`sys_user.username` / `sys_config.config_key` / `sys_dict_type.dict_type` 唯一索引不含
  `delete_time`。软删后重建同名 → `1062`，而 `findOneBy` 因软删过滤查不到 → 界面只报「数据库操作失败」。
- 修法：迁移 `1767000024000-FixSoftDeleteUniqueIndexes` 把唯一键扩为 `(列, delete_time)`
  （MySQL 里 NULL 不冲突 → 活行唯一、墓碑行可重复）；实体同步改 `@Index(..., ['...','deleteTime'])`。
- 坑：`sys_config` / `sys_dict_type` 的**旧索引名恰好等于目标名**，初版迁移「名字存在就跳过」
  导致什么都没改 —— 实测发现后改为「按列组合判断 + 临时名 → 删旧 → RENAME」。
- 验证：三个探针各自插入 → 软删 → 重插，全部成功（各 2 行 = 1 墓碑 + 1 活行）。探针已物理清理。

### P1-3 Swagger 生产公开（已修）

- `setup-app.ts` 无条件装 Swagger，`/api/docs-json` 匿名 200。
- 修法：`app.swaggerEnabled`，缺省 `NODE_ENV !== 'prod'`，显式 `SWAGGER_ENABLED=true` 才开。

### P2-2 删除保护不对称（已修）

- 用户：`UserService.remove` 现在拒绝「删自己」与「删持有 `level=0` 角色的账号」——
  与 `RoleService` 的「内置角色不可删」对称（那边护角色，这边护持有者）。
- 部门：`DeptService.remove` 增加「部门下仍有用户」拒删。`sys_user.dept_id` 无外键，
  删部门会让 deptId 悬空 → dataScope 静默失权，界面无异常。

### P2-3 覆盖率口径失真（已修）

- `vitest.config.ts` 无 `coverage.include` 时只统计「被测试 import 过」的文件 → 77% 虚高。
- 改为全量 `src/**`（排除 dto/entity/migration/scripts 等），**真实 18.93%**。不设 threshold：
  业务行为靠 110 条 e2e，拿单测覆盖率当门禁会逼人写假用例。

### P2-4 审计只记「调了什么」（已修）

- `sys_audit_log.detail` 列一直存在但全仓无赋值。
- 修法：`@Auditable({ capture: 'body' })` 默认记入参（`false` 可关），由 `AuditInterceptor`
  统一脱敏：password/newPassword/token/captchaCode 等置 `***`，Buffer → `[binary]`，
  超 2000 字符截断（防一个附件上传把 detail 写爆）。前端详情抽屉已有 `prettyDetail()`。

### P2-6 登录日志无留存（已修）

- `sys_login_log` 只增不减（审计有清理，登录日志没有）。
- 修法：`LoginLogService` 每小时分批清理，天数取 `sys_config.loginlog.retentionDays` →
  `LOGINLOG_RETENTION_DAYS` → 默认 90；test 环境跳过。

## 4. 决策与修复（第二轮，按人拍板）

### multer high → 定点 override（已修）

- `server/pnpm-workspace.yaml` 加 `overrides: multer: '>=2.5.0'`（只钉这一个传递依赖，
  **不动 @nestjs/* 主版本**）。install 后 `multer 2.4.0 → 2.5.0`，lock 只变 11 行。
- 验证：`pnpm audit --prod` 从 1 high + 2 moderate → **0 high + 2 moderate**
  （剩下的是 `typeorm→glob/minimatch`，不在请求路径上）；
  `test/file.e2e-spec.ts` **20 条全过**（上传/秒传/MIME 判定/413/bizType fail-closed/绑定/下载/删除）。
- 未来 upstream 跟上后可删掉这条 override（`pnpm why multer` 看实际来源）。

### 外键 → 不加（已拍板）

- 决策：**有意不加 FK**，只把理由与补偿写进 `docs/坑与约束.md`「数据库 / 迁移」。
  核心：软删让 FK 失去意义（父子行都在，永远满足）；批量删除顺序会变成隐式契约
  （MySQL 不支持延迟约束）；派生项目要做数据手术。
- 补偿：应用层「有引用就拒删」（dept / role / user）+ 关联表唯一索引 + e2e 归零断言，
  并附一条孤儿巡检 SQL（每月跑）。

## 5. `scope=SCHOOL` → 落地（已修，选 A）

- 决策理由：「全校通报」是校园安全的真实场景（警示/催办）；
  模板留一个假字段比没有更糟 —— 派生项目会照抄。
- 后端：`visibility()` 加 `OR h.scope = 'SCHOOL'`。放在 **SQL 层**（结果集过滤会让分页
  `total` 不对）；详情与附件鉴权（`canAccess`）复用同一套规则，所以 SCHOOL 单的
  附件同样全校可见，语义一致。
- 边界：`@RequiresPermissions(hazard:report:list)` 仍然是第一道门 ——
  全校通报**不是**「不需要权限」，而是「有列表权限的人都能看到」。
- 前端：上报表单加「全校通报」单选 + 橙色提示（“所有能进后台的人都看得到，
  包括标题/地点/附件，请确认可公开”）；列表筛选区补「可见范围」下拉
  （后端早支持 `?scope=`，此前前端没控件，属于死参数）。
- e2e：`hazard.e2e-spec.ts` 新增一条 —— operator 上报 SCHOOL 单 → 信息中心可见、
  详情 200；对照组 DEPT 单仍 404。首跑拓到一个“用例写错账号”的插曲：
  `manager_bw`（部门管理员）的 CASL 规则只有 read/accept/reject/rectify，
  **没有 create**，本来就不能上报 —— 改用 operator 才对（顺带证明权限分层有效）。
- 文档：`docs/隐患闭环.md` §2 由“三层并集”改为“四层并集”，并说明两层职责。
