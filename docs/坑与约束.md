# 坑与约束（血泪清单）

> **代码里看不见的东西**：看起来是对的，只有踩过才知道会炸。
> 规则：**只增不删**（除非确认彻底不适用）；每条尽量带一句「为什么 / 怎么避开」。
> 某些坑在专题文档里有详细版，此处只留指针。

## ESM / 构建

- 相对导入必须带 `.js` 后缀（`nodenext`），否则 TS2835。
- 禁 `src/...` 路径别名；`__dirname` 用 `import.meta.dirname`；内置模块加 `node:`。
- PM2 跑 Vite 必须指 `node_modules/vite/bin/vite.js`。
- dev Vite 必须加 `--strictPort`（防止端口漂移，同机共存前提）。

## 数据库 / 迁移

- **迁移按类名判重，不按 timestamp**：换号（改名）等于新迁移。
- 已跑迁移**不可改**，修正一律追加；新库必须补基线迁移（`CreateCoreSchema`）。
- `DB_SYNCHRONIZE=true` 与迁移并存 → synchronize **抢先改表**，迁移 DDL 从未生效。三份 `.env` 一律 `false`。
- 迁移 DDL 必须幂等：`hasColumn()` / 查 `information_schema` 后再 ALTER。
- 迁移目录 `dist` 与 `src` 并存，`migration:run` 实际走 `dist/`。
- MySQL 只允许**一个自增列** + DDL 隐式提交。
- `docker exec mysql -e` 多表 DELETE 必须 `-D` 选库；`-uroot -p123` 直传会 `Access denied`，须 `sh -c "mysql -uroot -p\"\$MYSQL_ROOT_PASSWORD\"..."`。
- 终端字符集不设时中文显示 `?????`（显示问题，非数据问题）。
- `CAST(x AS CHAR)` 继承 `collation_connection`。
- **一库一账号，禁止跨库 GRANT**（`server/sql/databases.sql` 是唯一定义，台账 `docs/库台账.md`）。
  旧写法是单个 `template`@`%` 同时 `GRANT template.*` + `template_prod.*` —— 后果不是
  「不够优雅」，是 **dev 进程手里的凭据能读写生产库**。现在账号 `<库名>_<角色>` 只授自己的库，
  生产库对 dev 进程物理不可达。派生时 `rename.sh --env` 已按角色写账号，别再手改回项目名。
- **MySQL 跑在 Docker 里时，账号 host 必须写 `%`**：宿主端口映射后连接来源是 docker 网关
  （172.x），不是 `127.0.0.1`。写 `'user'@'127.0.0.1'` 得到的是 `Access denied`，
  很容易误判成密码错/配置错，绕一圈才发现是 host 位。安全边界靠「一库一账号」，不靠 host 限制。
- **MySQL 没有 `RENAME DATABASE`**。改名只有两条路：dump + restore（prod / dev 才值得），
  或直接 DROP 重建（tmp 类库）。`template_test` → `template_tmp` 走的是后者：
  tmp 库本来就该可丢弃，**不需要为改名搬数据**。
- **真密码不许写进被版本管理的 SQL**：`server/sql/databases.sql` 会提交并随 SVN 分发给
  派生项目，把本机密码填进去 = 把密码发给所有副本（且 git 历史里擦不掉）。
  该文件只留 `<改我-dev|prod|tmp>` 占位符，真密码只落（已 gitignore 的）三份 `.env`，
  由 `scripts/db-apply.sh` 在 `mktemp` 渲染后执行、退出即删。
  出现过的错误版本已回滚为占位符 —— 但**如果这份文件曾被提交/分发过，密码就该换**。
- **业务账号建不了库**：一库一账号后，`GRANT ALL ON <库>.*` 不含 `CREATE DATABASE`。
  任何「新建目标库」的动作（恢复演练 `restore.sh`、`db-reset.sh`）都要**管理员连接**，
  接口统一为 `MYSQL_ADMIN` / `MYSQL_ROOT_PASSWORD`。

## TypeORM / 实体

- **联合类型字段必须显式 `type`**（否则元数据推断错）。
- `level` 无数据库默认值：绕过 `RoleService` 直接 `repo.save(Role)` 必须自己给 `level`。
- `allocateLevel()` 两处 `withDeleted()` 不能省（否则软删角色会撞唯一约束）。
- 软删 + join 过滤 = **静默撤权**（已用「有持有者拒删」堵）。
- 建表基线原则：已跑迁移不可改，修正一律追加。

## 权限

- 接口（DTO）只收**具体权限码**；`*` / `!` 只由迁移/seed 写。
- **权限串混用不可判定**：`*:*:*` 必须独占。
- 权限匹配有**三份副本**（后端权威 + `web_admin` + `web` 最小壳），必须同源：
  `server/src/common/authz/permission.util.ts`、`web_admin/src/utils/permission.ts`、`web/src/utils/permission.ts`。
  ⚠️ 曾因「注释写着一份、实际三份且已漂移」差点漏改，故一致性由
  `server/test/unit/permission-util.spec.ts` 的**对照单测**钉住：它同时 import 三份实现，
  用同一张用例表逐条比对。**新增匹配分支时先改那张表**（表红了再去补三份实现）。
- 权限清单**不参与鉴权**：`RbacGuard` 只看 `sys_role.permissions`；清单为空不影响鉴权。
- **含 `*` / `!` 的角色，界面权限区必须只读**（如校级管理员 `*:*:*,!system:*`）：
  这类码接口一律拒收，树里放行也会被 DTO 拦；保存时只下发 roleName / dataScope / status。
  判据用「权限串里有没有 `*` 或 `!`」，**不要用 `isBuiltin`** —— 部门管理员、业务操作员、审计员同为内置角色，
  权限为空，必须允许配置。踩坑记录：曾只锁 `level === 0`，编辑校级管理员时前端兜底校验报「权限码格式非法」。

## 配置 / 安全

- **`req.ip` 默认不可信**：拓扑是「浏览器 → Nginx → Node」，不配 `trust proxy` 时 `req.ip` 恒为
  127.0.0.1。后果：① 限流按 IP 计数 → **全校共用一份配额**，一人能把全校刷成 429；
  ② 审计 / 登录日志 IP 全同 → 出事查不到人。
  修法：`setup-app.ts` 设 `trust proxy = TRUST_PROXY`（缺省 1 = Nginx 一层）；Node 直连对外才填 `0`。
- **限流键 = IP + 路由**（`ThrottlerGuard.generateKey`），不是「IP + 全局」。所以单人刷
  登录页不会连带正常业务接口 —— 但前提还是上一条的 IP 可信。
- **e2e 必须关限流**（`.env.test` `THROTTLE_ENABLED=false`）：每个用例都要登录拿 token，
  全来自同一 IP，登录接口 5/分钟 → 测试随机 429，表现是「时好时坏」。
- **`new HttpException('msg', 状态码)` 的 `getResponse()` 是裸字符串**，而内置异常
  （`NotFoundException` 等）走 `createBody` 生成对象 —— 所以「字符串构造 + 非 500 状态码」
  是唯一会踩的分支。全局过滤器早期忘了在这一支回写 `code`，导致 HTTP 429/403 但
  `body.code=500`，前端按 code 判会误报成「服务器错误」。已有回归单测
  `test/unit/exception-filter.spec.ts`。
- **环境变量校验在启动时执行**（`src/core/config/env.validation.ts`，zod）：
  `NODE_ENV=prod` 时拒绝 <32 字符或模板值的 `JWT_SECRET`、拒绝 `DB_SYNCHRONIZE=true`。
  校验失败 = 进程起不来（`Config validation error: ...`），这是**有意为之**：宁可起不来，
  也不要带着弱密钥 / 共享 dev 密钥上线。
- **dev / prod 必须真正隔离**：`JWT_SECRET`、`DB_DATABASE`、`REDIS_DB` 三样都要分开。
  只改端口不叫隔离 —— 共库/共密钥下 dev 的操作会串到 prod（会话互踢、数据互相覆盖）。

## Zod / DTO

- **Zod 4 `.partial()` 保留内层 `.default()`** → PUT 退化为整条覆盖；必须用 `updateSchemaOf()`（`src/common/dto/update-schema.util.ts`）。
- 时间字段用 `z.iso.datetime()`；查询空串 = 未填（`z.preprocess` 归一）。
- 单测里 `Reflect.defineMetadata` 必须先 `import 'reflect-metadata'`。

## 树形数据（dept / menu）

- **改子孙 `ancestors` 必须带逗号边界**：`LIKE '0,1%'` 会误伤 `0,10`（id=1 的**兄弟**子树），
  一次挪部门静默改坏别的枝条 —— 而 `ancestors` 正是数据范围求子树的依据，权限跟着错。
  正确写法 `(= :p OR LIKE :pc)`，`pc = '${oldPrefix},%'`（`menu.service.ts` 一直是对的，
  `dept.service.ts` 漏了）。回归：`test/dept-tree.e2e-spec.ts`（把写法改回去即红）。
- **`parentId` 要能表达「移到顶级」**：`z.coerce.number().int().positive()` 会把 `null`/`''` 强转成
  `0` 再被 `.positive()` 拒掉（`0` 直接也拒），结果是**节点一旦挂下去就永远搬不回根**。
  统一用 `common/dto/parent-id.util.ts` 的 `parentIdSchema`（dept / menu 共用一个实例）。
  注意 `.optional()` 在**外层**：未传仍是 `undefined`（= 用户没提这个字段），与「显式置根」分开。

## 响应包装

- **不可用「返回体有没有 `code` 字段」判断是否已包装**（`TransformInterceptor` 旧写法
  `data?.code !== undefined`）：任何自带 `code` 列的业务对象（单据编号 / 字典编码 / 行政区划码）
  被单个详情接口直接 `return` 时会被**静默少包一层**，前端拿到 `{code,...}` 而 `data` 是 `undefined`，
  不报错、只是那个接口数据变空。想自定义 `msg` 就显式 `@Keep()` + `return success(...)`。
  回归：`test/unit/transform.interceptor.spec.ts`。

## 前端

- 刷新 404 根因：守卫里动态路由注册晚于 `to.meta.public` 早退 → 深链命中 catch-all。修复：注册提前 + 按 `{ path: to.fullPath, replace: true }` 重解析。
- **「没权限」不能表现成 404**：侧边栏用 `/menu/routes`（按权限过滤），**路由注册必须用
  `/menu/pages`（不过滤）**。否则无权限的地址在路由表里不存在 → 命中 catch-all →
  渲染「404 页面不存在」，用户以为页面没了。现在全量注册 + 守卫读 `meta.perm` → 403；
  真不存在的路径仍是 404。两者混用（都拿 `routes`）就是这个 bug 的成因。
  附带修好一处：隐藏页面（`visible=0`）以前也不可访问（`routes` 滤掉了），现在能打开。
- **空壳目录也会 404**：菜单 M 类型 `perms` 是空串，如果把「空 perms 视为命中」
  用在目录上，子页面全被过滤时目录自己还留着 → 侧边栏一个点进去 404 的空气节点。
  规则：**目录不单独判权限，只能由「有命中权限的后代」通过祖先链带进来**；
  前端侧边栏也只把 `type==='C'` 渲染成可点项。
- `crypto.randomUUID` 有安全上下文限定 → 用 `getRandomValues` 自拼 UUID v4。
- `ElTree` 的 `filter-node-method` 类型是 `TreeNodeData`，自定义节点需 `Record<string, unknown>` 再取值（否则 vue-tsc TS2322）。
- 业务异常走 HTTP 200 + `body.code`；前端 catch 判 `error instanceof ApiError`。
- **列表页写法固定**：`useCrud`（查询/分页/加载/删除）+ `DataTable`（列配置 + 分页条）+ `FormDialog`（表单）。
  表单有联动（如菜单类型切换字段）或自定义控件（权限树、部门树选择）时继续手写弹窗，别硬塞配置。
  树表接口整棵返回、无分页，**不套 useCrud**，`DataTable` 传 `:pagination="false"` + `default-expand-all`。

## 环境 / 网络（WSL2）

- **WSL2 默认没有 IPv6 出口，但很多 CDN 只给 AAAA**。表现是「下载卡住、不报错、也不超时」，
  很容易误判成"被墙"。诊断三步：`getent hosts <域名>` 看是否只有 IPv6 →
  `curl -4 -sI` 与 `curl -6 -sI` 对比 → 确认后加 `NODE_OPTIONS=--dns-result-order=ipv4first`
  或在 `/etc/gai.conf` 里让 `::ffff:0:0/96` 优先。
  已踩：`cdn.playwright.dev`（Playwright 浏览器）、`mirrors.cloud.tencent.com`（apt 源）、
  `registry.npmmirror.com`。`registry.npmjs.org` 是只走 IPv4 的，所以 pnpm 一直正常。

## 部署 / 运维

- **迁移里混了演示数据**：`1767000008000-SeedHazardDemo` 会建演示部门+4 个演示账号
  （密码 `Demo@12345`）。已在 `up()` 开头加 `NODE_ENV=prod` 短路（**不是**靠注释提醒），
  fresh 部署到生产不会再生成。派生项目若要自带 seed，照这个写法在**环境上断开**，
  不要指望人工记得删。
- **权限清单是反射来的，只看得见路由上的 `@RequiresPermissions`**：只在 service 里消费的码
  （如 `system:file:remove`）不登记进 `permission-catalog.ts` 的 `EXTRA_PERMISSIONS`
  就永远不会进 `sys_permission` → 角色界面勾不到 → **这条能力永远无法授予**，
  而且不报错（代码里那个 `matchPermission` 分支静默成为永远走不到的死路径）。
- `template.sh stop` 会摘 nginx 软链 → 端口无监听（预期行为，非故障）。
- prod 显式传 `NODE_ENV=prod` 跑 `migration:run`。
- **prod 换独立库名后，必须先建库 + 跑迁移再启动**：`template.sh prod start` 第 2 步就是
  `migration:run`，库不存在会直接失败退出（这是好事：不会静默退回共用 dev 库）。
- **Redis 客户端必须显式关连接，否则进程永远不退出**：ioredis 的 socket 是活跃 handle，
  `app.close()` 不会帮你关。后果不是「内存泄漏」而是更直接的：`node dist/scripts/authz-sync.js`
  跑完 sync 后**停在事件循环里不退** → `template.sh prod start` **无超时地卡在第 4 步**；
  SIGTERM 优雅停机名存实亡（进程不自己退，只能等 PM2 `kill_timeout` 到了发 SIGKILL）。
  修法：`RedisService implements OnModuleDestroy` → `quit()`（发完在途命令再关），
  带 2s 兜底 `disconnect()`（Redis 不可达时 `quit()` 可能一直等）。
  回归单测 `test/unit/redis.service.spec.ts`。
  → **新增《外部连接》一律要问一句「谁在退出时关它」**（Redis / 存储 / 定时器 / 子进程）。
- Nginx 不占 80；`client_max_body_size` 三层对齐（20m ↔ `MAX_FILE_SIZE` 10MB ↔ 前端）。
- `authz:sync` 在 pm2 重载前跑，**失败只 warn 不阻断**。
- **恢复演练的目标库必须固定名**：旧行为 `<原库>_restore_<时间戳>` 每跑一次多一个库，
  几轮下来库表就散了（`DROP` 谁都不敢按）。现在是 `<项目>_tmp_restore`，先 DROP 再导入。
- **`mysqldump --databases` 的 dump 里带 `USE <源库>`**：原样灌进另一个库会**写回源库**，
  表现是「导入成功、目标库 0 张表」，最坏情况把生产库原地覆盖一遍。`restore.sh` 已剥掉
  `CREATE DATABASE` / `USE` 行；手工导入时记得 `mysql <db> < file.sql` 并先确认 dump 形态。
- **一库一账号后，演练要管理员连接**：业务账号没有 `CREATE DATABASE` / `GRANT` 权限，
  建演练库必须走 `MYSQL_ADMIN` / `MYSQL_ROOT_PASSWORD` / 容器回退。密码用 `MYSQL_PWD` 传，别进 argv。
- **备份脚本不能给库名默认值**：`backup.sh` 原来是 `${DB_NAME:=template}` —— 默认备份的是
  **dev 库**。cron 里漏传 `DB_NAME`，每天都会「备份成功」，而生产库一次都没备过，
  这种事故极其安静。现在 `DB_NAME` / `DB_USER` 都 `:?` 必填，缺了直接报错退出。
  同一条也适用于 `restore.sh`：它 source `server/.env.prod` 拿到的是 `DB_USERNAME`，
  只给 `DB_USER` 设默认值会**静默退回旧账号**，所以两者都要认。
- `edit` 多块原子性：一块 `oldText` 不匹配可能整批不生效，改后必须 grep 复核。

## 定时任务 / 数据回收

- **新写定时清理任务，三件事必须都有**（照 `file.cleanup.task.ts` 抄）：
  1. `app.env === 'test'` 直接 `return` —— e2e 会断言表内容，后台任务删掉一行就是随机红；
  2. `running` 重入闩 —— 上一轮没跑完就跳过，不然慢查询下会堆出多份并发删除；
  3. `try/catch` 吃掉异常 —— `@Cron` 回调里抛出去会把进程带崩（不是“记一条日志继续”）。
- **清理只动终态，永不动物流中间态**：`sys_outbox` 只删 `sent`/`failed`，删 `pending`/`processing`
  等于凭空丢业务事件。
  **例外：`sys_idempotency` 按 `expire_at` 删（不看 status）** —— 那里的 `processing`
  只是「有请求正在执行」的占位；进程崩掉就会留下永不释放的占位，客户端重试只能拿 409。
  按过期时间回收正是它的**自愈机制**；反过来若只删 `done`，卡死的占位就永不消失。
- **保留期按 `create_time` 算，不按 `sent_at`**：`failed` 事件永远没有 `sent_at`，
  拿它做判据就只能漏掉整整一类（死信）。索引也跟着建成 `(status, create_time)`，
  否则每小时一次回收都会退化成全表扫。
- **幂等占位冲突必须有限重试**：老实现是「冲突 → 查不到就递归再试」，唯一键冲突
  恰好发生在并发写同一 key 时，递归深度直接由并发度决定 —— 高并发下是栈溢出，
  而不是一个可预期的 409。现在是 3 次上限 + 退避 + `ApiException(409)`。

## 密码 / 会话

- **改密必须使会话失效**（`UserService.updatePassword` 内置）。改密的常见动机是
  「怀疑密码泄露」，如果旧 token 还能用到 TTL 到期，改密就是自我安慰。
  副作用：改密人自己也被踢下线，前端据此跳登录页。
- **管理员重置不要求原密码**：管理员既不知道也不应该知道。权限边界靠
  `system:user:reset-pwd`，不靠「他知道旧密码」；否则只能逼出共享口令，审计反而追不了责。
- **密码策略单点**：`server/src/modules/auth/dto/password.dto.ts` 的 `passwordSchema`
  同时被「创建用户」和「改密/重置」引用。两处各写一份的结果是“建账号能过、改密过不了”
  （或反过来），而且两边前端提示也对不上。

## 数据范围（dataScope）

- **调 `dataScope.resolve()` 时直接传 `user`，不要手搓 `{ userId, deptId }`**。
  手搓会把 `dataScopeDepts` 丢掉，而 `CUSTOM` 的空集合语义是 **fail-closed** ——
  表现不是报错，是"这个角色什么都看不到"。已踩一次（hazard/user 三处调用点）。
- **CUSTOM 的部门集合进会话，不进 JWT**：JWT 只放 userId/username（否则改权限要等 token 过期）。
  改了角色的部门集合要**失效持有人会话**，否则旧快照继续生效（与权限码同一套逻辑）。
- **空集合 = 不可见**，绝不退化成"不过滤"。界面拦空提交，接口也允许空（两段式操作需要），
  所以这条兜底必须在查询层。

## 审计

- **`AUDIT_MODE=sync` 不等于「审计与业务同事务」**。审计写在自己的连接上，业务事务
  已经提交，审计失败回滚不了业务 —— 这是 append-only 审计的固有取舍，不是实现瑕疵。
  `sync` 买到的是「延迟和失败在请求上可见」，不是原子性。
- **审计拦截器不能用 `tap` 做同步等待**：`tap` 的副作用回调不 await Promise，
  在那里 `await` 只能得到「语法上当等了」的假同步。要等就得用 `mergeMap`/`concatMap`。
- **审计最终失败必须把完整条目打进日志**。只记 `action + traceId` 等于
  「知道丢了一条，但不知道丢的是什么」—— 事后无法重建，等保检查时照样是缺失。
