# 文件与附件

> 底座能力，**不含任何业务名词**。业务模块通过注册表接入，底座不认识 `hazard` / `notice` 这些名字。

## 1. 定位

四层职责，只有第三层是本项目写的：

| 层 | 谁负责 | 说明 |
|---|---|---|
| 对象存储 | `@nestjs/storage` | `S3Disk` / `LocalDisk` / `InMemoryDisk` 同一套 `put/get/stat/delete/signedUrl` |
| 收件安全 | Nest 12 Pipe + `file.security.ts` | Magic Number、大小上限、扩展名黑白名单、文本内容特征 |
| **元数据 · 多态绑定 · 权限 · 审计 · 回收** | **本项目 `modules/file`** | 底座价值所在；`@nestjs/storage` 不管这些 |
| 业务语义 | 业务模块 | 谁能看某业务对象的附件、允许哪些用途 |

结论：**不自己写存储 SDK，也不引 AWS SDK**。

## 2. 数据模型

### `sys_file`

关键字段：`sha256`、`original_name` / `ext` / `mime` / `size`、`disk` / `object_key`（不外泄）、
`uploader_id` / `uploader_name` / `uploader_dept_id`、`status`（`TEMP`/`ACTIVE`）、`ref_count`、`expire_at`。

唯一键 `uk_file_sha_uploader(sha256, uploader_id, delete_time)`：

- 同用户重复上传同内容复用同一条记录（秒传），删除权只作用于自己。
- 不单独用 `sha256` 唯一：那会让不同用户共享同一行，产生「知道摘要就能确认别人有某文件」的泄漏，删除权也互相干扰。
- 把 `delete_time` 放进唯一键，让软删行不阻塞重新上传（MySQL 唯一索引里 `NULL` 互不冲突）。

### `sys_file_link`

`(file_id, biz_type, biz_id, biz_field)` 唯一。一个文件可被多个业务引用，一个业务对象可有多个附件，`biz_field` 区分用途。

**不继承审计基类、不软删**：解绑就是物理删除，否则唯一键被历史行占住，「解绑后再绑定」会冲突。留痕靠审计日志。

## 3. 对象键

```
{yyyy}/{MM}/{sha256 前两位}/{uploaderId}/{sha256}.{ext}
```

- 全部服务端生成，**不含任何用户输入** → 杜绝路径穿越与文件名注入。
- **按上传人隔离**：一个对象键唯一对应一条记录，删字节不波及别的文件。
- 同用户同内容同键，覆盖写天然幂等；按日期分片，便于生命周期与归档。

## 4. 收件校验（四层，全 fail-closed）

| 层 | 实现 | 拦什么 |
|---|---|---|
| 传输层 | multer `limits` | 超限 **413**，不进内存、不落盘 |
| 大小 | `MaxFileSizeValidator` | 兜底 |
| 内容类型 | `FileContentTypeValidator` | 二进制看 Magic Number（`file-type`）；文本看内容特征 |
| 文件名 | `FileExtValidator` | 黑名单（exe/脚本/镜像）+ 白名单 |

**为什么不用内置 `FileTypeValidator`**：它检测不到 Magic Number 时回退到**客户端声明的 `mimetype`**，而 CSV/TXT/MD 本就没有文件头、声明五花八门，一旦回退等于「信客户端」。所以拆两条路：

- **二进制**：交给 `file-type`，客户端声明被覆盖成真实类型。
- **文本**（`txt`/`csv`/`md`）：不看声明只看内容（命中 `#!`、`<?php`、`<%`、`<script` 即拒），并把 `mimetype` 规范化。`TEXT_CONTENT_BLOCKLIST` 是必需的（`evil.sh` 改名 `evil.txt` 没有文件头）。

**业务策略只能收紧**：全局 `ALLOWED_EXTENSIONS + MAX_FILE_SIZE`，业务 `FileBizHandler.accept` 取交集 / 更小值。
带 `bizType` 上传即按业务策略校验；先上传后绑定用全局策略，**绑定时再按业务策略复验**。

## 5. 去重（秒传）

`(sha256, uploader_id)` 命中未删记录 → 返回已有元数据、`deduped: true`、不写盘。
**只做同用户秒传，不做跨用户去重**（不同用户各存一份字节）。

放弃跨用户去重的原因：共享字节会让删除必须判断「还有没有别人在用」，而**判断与删字节之间必然有窗口** —— 并发下可能删掉别人刚上传的同内容字节。校内附件重复率低、单文件 10MB 封顶，多存几份的代价远小于并发风险。

若将来存储成为瓶颈，正确做法是引入**独立引用计数表**（`(object_key)` 主键 + 原子 `ref_count` + 行锁），而不是「删前查一下」。

## 6. 访问控制（三条通路，都不满足即 404）

```
下载 / 详情：
  1. 我是上传人
  2. 我有 system:file:list（文件管理员）
  3. 已绑定业务对象，且我通过该业务对象的访问判定
```

第 3 条是关键：**附件权限跟业务对象权限同源**（如隐患附件用 `HazardService.canAccess`，与列表同一套数据范围）。统一返回 404 而非 403：不泄漏「id 存在但你不能看」。

绑定/解绑走 `FileBizRegistry`，**未注册的 `bizType` 一律拒绝**（fail-closed）；默认放行会让新业务忘注册时越权读附件。

上传/下载/删除**自己**的文件不需权限码，靠归属 + 业务可见性判定。`DELETE /file/:id` 因此**不挂权限码**（挂了会把「删自己传错的文件」挡掉），边界在 `FileService.assertCanWrite`。

`assertCanWrite` 的实际判定：**上传人本人 ‖ 持有 `system:file:remove`**（第二个分支给文件管理员删他人文件用）。
这个码**没有挂在任何路由上**（上段已说明原因），所以它在 `permission-catalog.ts` 的
`EXTRA_PERMISSIONS` 里显式登记 —— 不登记就永远不会出现在 `sys_permission`，
角色界面勾不到它，这条能力就永远无法授予（曾经就是这个状态）。

> 注意：内置校级管理员（level 1）的权限串是 `*:*:*,!system:*`，`!system:*` 会排掉整个
> system 域 —— 即**默认只有超管能删他人文件**。需要让别的角色也能删，就在角色界面
> 显式勾上 `删除任意文件（非上传人）`。

## 7. 回收

```
上传 → TEMP（expire_at = now + 2h）
  ├─ 绑定 → ACTIVE（ref_count++，expire_at = null）
  │    └─ 解绑 → ref_count 归 0 时回 TEMP，重新计时
  └─ 超期且 ref_count = 0 → 软删元数据 + 删物理对象
```

`TEMP_FILE_TTL_HOURS = 2` 覆盖「上传→填表→提交」窗口，又不让放弃的文件占存储过夜。
`FileCleanupTask` 每小时一次（带重入保护）；`NODE_ENV=test` 时跳过。已绑定（`ACTIVE`）文件永不因超期被删。
回收条件带兜底：`expire_at IS NULL` 的 TEMP 行也一并回收（否则永久逃逸）。

物理删除失败只记 warn：元数据已删，残留对象不构成越权；孤儿对象靠运维对账 / 存储生命周期规则清理。

## 8. 下载

**走后端代理，不直链**（唯一能同时满足鉴权、隔离、审计、防盗链）。

```
GET /api/v1/file/{id}/download
→ 鉴权（§6）→ 流式转发
  Content-Type / Content-Disposition（RFC 6266，中文走 filename*=UTF-8''）
  Content-Length / ETag / X-Content-Type-Options: nosniff / Cache-Control: private, no-store
```

前端用 `utils/download.ts` 的 `downloadFile()`（axios 拿 blob 再另存）—— `<a href>` 带不上 `Authorization`。
私密附件**不引 `signedUrl`**：签名链接泄漏后在有效期内任何人都能下载，绕过审计。

## 9. 存储引擎（可拔插）

```env
STORAGE_DRIVER=s3|local|memory     # memory 仅测试（e2e 用它，不碰 MinIO）
STORAGE_DISK=default
STORAGE_S3_ENDPOINT=http://127.0.0.1:9010
STORAGE_S3_BUCKET=template
STORAGE_S3_FORCE_PATH_STYLE=true   # MinIO 必须 true
```

换引擎只改配置，业务代码零改动。多盘并存（图片盘 / 归档盘）时多配一个盘 + `storage.disk('archive')`，`sys_file.disk` 已记录落盘位置。

**为什么不自己写适配器**：`@nestjs/storage` 本身就是抽象（Nest 官方组织，零运行时依赖，自实现 SigV4），再包一层 `StoragePort` 是冗余（早先那层已删）。对比过的替代品（`@fozooni/nestjs-storage` peer 只到 Nest 11；`minio@8` 自写要管 Range/ETag/签名；`unstorage` 是 KV 语义）都不合适。

## 10. 接入新业务（照抄）

`modules/hazard/adapters/hazard-file.handler.ts`：实现 `FileBizHandler`（`canAccess` / `fields` / 可选 `accept` / `onBound`），在 `onModuleInit` 里 `registry.register('xxx', this)`。

两件事必须做对：

1. **`FileModule` 要 import**：`FileBizRegistry` 的 provider 按模块可见性解析，不 import 会拿到另一个实例（注册了也查不到）。
2. **`canAccess` 必须复用业务列表的可见性规则**，不要另写一套。

## 12. 已知限制

- **单文件上传**：`POST /file` 一次一个；多文件由前端逐个上传。
- **无病毒扫描**：ClamAV 挂载点应在 `FileService.upload` 落盘前，属部署态能力。
- **无图片处理**：缩略图/水印未做。
- **删除即解绑**：删文件连带解除所有业务绑定，语义是「这个文件不要了」，不做「被引用就拒删」；留痕靠审计 + 服务端日志。
- **临时对象残留**：物理删除失败只记 warn，需运维对账或存储生命周期规则兜底（暂无对账脚本）。
