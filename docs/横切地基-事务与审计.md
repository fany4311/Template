# 横切地基：事务 / 幂等 / 审计 / Outbox

> 让「事务、一致性、幂等」与「独立审计管道」成为所有业务切片可复用的地基。
> 机制细节在代码：`src/core/*`、`src/common/*`、`src/modules/{audit,idempotency,outbox}/*`。

## 1. 事务（一致性）

`@nestjs-cls/transactional` + `@nestjs-cls/transactional-adapter-typeorm`（与 `nestjs-cls` 同源，ESM 友好）。

- 装配在 `app.module.ts` 的 `ClsModule.forRoot({ plugins: [ClsPluginTransactional] })`。
- 声明式：service 方法加 `@Transactional()`。
- 事务内取仓库**必须**用 `this.txHost.tx.getRepository(Entity)`，否则 `@InjectRepository` 的仓库不参与事务。
- 正常返回 → 提交；抛错 → 回滚；嵌套默认 join 现有事务。

```ts
async create(dto: CreateUserInput) {
  return this.txHost.withTransaction(async () => {
    const repo = this.txHost.tx.getRepository(User);
    // ... 校验 + 写入
  });
}
```

> 约定：**写操作**用事务；**读操作**可用注入仓库。跨聚合一致性走 Outbox。

## 2. 独立审计管道

原则：审计与业务**解耦**、append-only、失败不反噬业务、可换底座。

```
@Auditable({...}) → AuditInterceptor（全局，无元数据 no-op）
                  → AuditService.record(entry)
                      ├─ AUDIT_MODE=async（默认）→ 投递进程内事件，不 await
                      └─ AUDIT_MODE=sync        → 当前请求内 await 落库
                  → AuditListener（@OnEvent，仅 async）→ append-only 写 sys_audit_log
```

- 元数据：`@Auditable({ action, resourceType, resourceIdParam })`。
- 记录字段：traceId / actor / action / resource / result / errorCode / method / path / ip / UA / durationMs / createTime。
- 成功与失败都投递（`fail` 带 `errorCode`）。
- `sys_audit_log`：append-only、不软删、关键列有索引；后续按月分区、留存 ≥3 年。
- **失败兜底**：两种模式都先重试 3 次（50ms / 200ms 退避），最终失败把**完整条目**
  写进 pino error 日志（可从日志重建）。老实现只记 `action + traceId`，等于知道丢了什么业务
  但不知道丢了什么内容。
- **`AUDIT_MODE=sync` ≠ 同事务**：审计写在自己连接上、业务事务已提交，失败回滚不了业务。
  `sync` 买到的是「延迟 / 失败在请求上可见」，不是原子性 —— 这是 append-only 审计的固有取舍。
- 拦截器用 `mergeMap` 而非 `tap`：`tap` 的副作用回调不 await Promise，在那里 `await` 是假同步。
- 停机：`AuditListener.onApplicationShutdown` 先排空在途写入。
- 敏感入参写 `detail` 前必须脱敏（PII）——**脱敏器尚未实现，当前是调用方责任**（见 `整体方案与选型.md` §2 警示表）。

## 3. 幂等（Idempotency）

自研 `@Idempotent()` + `sys_idempotency` 表（**DB 持久化**，多实例强一致）。

```
@Idempotent({ scope, required, ttlSeconds })
  → IdempotencyInterceptor（全局，无元数据 no-op）
  → 占位 insert(status=processing)   // 唯一键冲突 = 重复请求
  → 执行业务 → complete(status=done, responseBody=包装后响应)
```

| 场景 | 结果 |
|---|---|
| 首次 | 正常执行并记录响应 |
| 同 key 同内容 | 回放首次响应 |
| 同 key 不同内容 | `code 409` |
| 并发重复（首次处理中） | `code 409`（冲突重试上限 3 次 + 退避，不再无上限递归） |
| 业务失败 | 释放占位，允许重试 |
| 缺 `Idempotency-Key` | `code 400`（`required:false` 可关） |

- key = `${scope}:${userId}:${clientKey}`；客户端经请求头 `Idempotency-Key` 传入。
- **拦截器须在 Transform 之外层**（回放的是包装后的最终响应体）。
- 记录默认保留 24h（`expireAt`），由 `IdempotencyCleanupTask` **每小时**批量回收（500/批）。
  回收**按 `expire_at` 删、不看 status**：那里的 `processing` 只是「有请求正在执行」
  的占位，进程崩掉会留下永不释放的占位（客户端重试只能得 409），按过期回收正是它的自愈机制。

## 4. Outbox（可靠事件投递）

自研 Transactional Outbox（`sys_outbox`）。

- 业务在**事务内** `outbox.append(...)`，与业务数据同事务原子提交（回滚则事件也不存在）。
- `OutboxPublisher` 每 1s 轮询：`FOR UPDATE SKIP LOCKED` 抢占 pending → processing → 投递给已注册处理器。
- 处理器 `outbox.registerHandler(eventType, handler)`（业务模块 `onModuleInit` 注册）。
- 失败指数退避（1s,2s,4s…），超 5 次置 `failed`；卡死 `processing` 超 60s 回收为 pending。
- **至少一次语义，处理器须幂等**；无处理器的类型标记 sent（避免无限 pending）。
- 开关 `.env OUTBOX_ENABLED`（默认 true）。

用途：跨聚合一致性（如 `user.created`）与省平台同步的可靠投递底座。

- **终态回收**：`OutboxCleanupTask` 每小时删 `sent`（默认留 7 天）/ `failed`（默认 30 天，删前 warn）；
  保留期由 `OUTBOX_SENT_RETENTION_DAYS` / `OUTBOX_FAILED_RETENTION_DAYS` 覆盖。
  `pending` / `processing` **永不清理**（删了等于凭空丢业务事件）。
- 回收查询靠 `idx_outbox_status_create (status, create_time)`：保留期按**事件产生时间**算，
  不用 `sent_at`（failed 事件永远没有它）。

## 5. 密码与会话

- 自助改密 `POST /auth/password`：校验原密码 → 写新哈希 → **会话立即失效**。
- 管理员重置 `PUT /user/:id/password`：权限码 `system:user:reset-pwd`，不需要原密码 → 会话立即失效。
- 密码策略单点：`auth/dto/password.dto.ts` 的 `passwordSchema`（创建用户也引用它）。
