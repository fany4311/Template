# 部署端环境

## 基础环境

node `v24.21.0` / pnpm `12.5.1` / MySQL `8` / Redis `6`；6 核 / 8.9G。

## 组成

| 组件 | 位置 | 说明 |
|---|---|---|
| MySQL / Redis / MinIO | `~/Docker/*/compose.yaml` | 各自独立容器，`./data` 挂载 |
| 后端 | `trunk/server` | PM2 **fork 单实例**，`127.0.0.1:3000` |
| 后台 `web_admin` 产物 | `/var/www/template/admin` | 站点 `template-admin`，`:8080` |
| 前端 `web` 产物 | `/var/www/template/web` | 站点 `template-web`，`:8084` |
| Nginx | `sites-available/template-{admin,web}` | 两站点，**都不占 80** |

### 为什么是两个前端、两个站点

| | 后台 `web_admin`（8080） | 前端 `web`（8084） |
|---|---|---|
| 面向 | 超管 / 管理员 | 全体业务用户 |
| 内容 | 动态菜单 + 系统管理 + 隐患 | 目前是最小壳 |
| 准入 | 权限码 `console:access` | 任何能登录的账号 |

动机：**前端改版不用动后台、后台发版不影响前端**。两站点**共用同一后端**，`/api/` 都转发 3000，
token 天然互通。正因如此，后台准入**不能只在 Nginx 做** —— 真正的边界是每个写接口上的
`@RequiresPermissions`；前端 `console:access` 守卫只是顺手挡一下。

## 部署文件

```
deploy/
├── template.sh                          # 唯一入口：dev/prod 两族子命令
├── rename.sh                            # 派生改名：身份/文件名/端口一次替换
├── ecosystem.dev.config.cjs         # dev 三进程（后端 3010 + 后台 5183 + 前端 5184）
├── ecosystem.prod.config.cjs        # prod 单进程（后端 3000）
├── nginx/template-admin.conf # 后台站点（listen 是 __PORT__ 占位符）
├── nginx/template-web.conf   # 前端站点（同上）
├── .env.prod.example                # 生产环境变量模板
├── backup.sh                        # MySQL 备份（dump + gzip 校验 + sha256）
└── restore.sh                       # 恢复演练（默认恢复到临时库，不碰生产）
```

> `nginx/*.conf` 里 `listen __PORT__` **不是笔误**：安装时由 `template.sh` 的 `render_conf()`
> 用 `ADMIN_PORT` / `WEB_PORT` 渲染。**端口只有一个来源** = `template.sh` 的变量。
> 直接 `cp` 会留下 `__PORT__`，`nginx -t` 报 `invalid port` —— 这个报错就是提醒你走脚本。

## dev / prod 两套（可同时跑）

```bash
bash deploy/template.sh dev  start|stop|status|logs admin    # 3010 + 5183 + 5184
bash deploy/template.sh prod start|stop|status|migrate|web|restart
bash deploy/template.sh logs                                  # 生产后端实时日志
```

| | dev | prod |
|---|---|---|
| 进程名 | `*-dev`（3 个） | `template-api-prod`（1 个） |
| 后端 | **3010**（`.env.dev`） | **3000**（`.env.prod`） |
| 前端 | vite 5183 / 5184 | Nginx 8080 / 8084 |

端口为何都不是默认值（同机共存）：`BigScreen` 占 5173/5174/8081/8082。
**改端口三处必须同步**：`deploy/template.sh`、两个 `vite.config.ts`、Nginx conf（重渲染）。

### dev / prod 隔离：光改端口不算隔离

下面四项**必须两套不同值**，否则一套的数据/会话会串到另一套：

| 项 | dev | prod | 串了的后果 |
|---|---|---|---|
| `JWT_SECRET` | `...-dev-secret` | 独立 ≥32 字节随机串 | 两边 token 互相能用；改一边踢另一边 |
| `DB_DATABASE` | `template` | `template_prod` | dev 跑迁移/清数据会打到生产库 |
| `REDIS_DB` | `1` | `4` | 无关；**但**登录态/幂等键混在一起，一边清缓存踢掉另一边 |
| `STORAGE_S3_BUCKET` | `template` | 建议 `template-prod` | 上传的文件两边互见 |

`NODE_ENV=prod` 启动时会校验：`JWT_SECRET` <32 字符、或是模板/dev 默认值、或 `DB_SYNCHRONIZE=true`
→ **直接拒绝启动**（`Config validation error: ...`）。宁可起不来，也不要带弱密钥上线。

另一个容易漏的：`TRUST_PROXY`。拓扑是「浏览器 → Nginx → Node」，不配它 `req.ip` 恒为
`127.0.0.1` → 限流按 IP 计数时**全校共用一份配额**，审计/登录日志也查不到人。缺省即 `1`，
Node 直连对外（不经代理）才填 `0`。

## 首次部署

```bash
# 0. 容器
cd ~/Docker/{mysql,redis,minio} && docker compose up -d   # MinIO: 9010/9011

# 1. 建库建账号（一次）
#    **不要手敲 SQL**：库名/账号/授权的唯一定义在 `server/sql/databases.sql`，
#    一库一账号（template_dev / template_prod / template_tmp），一个账号只授自己的库。
#    理由与台账见 `docs/库台账.md`。
#    dev 库 template 与 prod 库 template_prod **必须分开**（见「dev / prod 隔离」）
MYSQL_ROOT_PASSWORD=<root密码> bash scripts/db-apply.sh

# 2. 生产环境变量（DB_USERNAME 必须是 template_prod，不是 template）
cp deploy/.env.prod.example server/.env.prod && vi server/.env.prod   # 按 TODO(部署端) 逐项填

# 3. 一键部署（依赖 → 迁移+种子 → 构建 → PM2 → 装两站点 → 两前端产物）
bash deploy/template.sh prod start
```

首次部署自带 **5 个内置角色 + 菜单树 + 字典 + 文件模块接入配置**。

> **生产库没有演示数据**：部门 / 4 个演示账号 / 演示隐患单只在 dev / test 生成 ——
> `1767000008000-SeedHazardDemo` 的 `up()` 开头遇到 `NODE_ENV=prod` 直接 return。
> 那 4 个账号（`operator_bw` / `manager_bw` / `manager_xx` / `auditor_school`，密码
> `Demo@12345`，明文写在迁移源码里随 SVN 分发）**不会出现在生产库**
> （实测：prod 全新库跑完迁移，`sys_user` 0 行、`sys_dept` 0 行）。
> ⚠️ 派生项目若要把演示数据当「初始化数据」用，请**另写 seed 脚本**并显式确认目标库，
> 不要把那条环境短路拆掉。

生产库**连超管都没有，且没有任何部门**。第一个管理员必须用脚本建 ——
密码是 argon2 哈希，**不能用 SQL 手写**；且因为生产库无部门，必须**先建根部门**
（`sys_user.dept_id` 没有外键，写个不存在的 id 不会报错，但会让数据范围（dataScope）错乱）：

```bash
# 1) 生成密码哈希
cd trunk/server && node -e "
const { hash } = require('@node-rs/argon2');
hash('换成你的强密码').then(h => console.log(h));"

# 2) 建根部门 + 超管 + 绑角色（一条事务，失败可回滚）
#    角色用 level=0 定位，别用会变的角色名
HASH='上一步拿到的哈希'
docker exec -i mysql mysql -uroot -p"$MYSQL_ROOT_PASSWORD" \
  -D template_prod --default-character-set=utf8mb4 <<SQL
START TRANSACTION;
INSERT INTO sys_dept (parent_id, name, ancestors, sort, status)
  VALUES (NULL, '长沙医学院', '0', 1, 1);
INSERT INTO sys_user (username, password, nickname, dept_id, status, post)
  VALUES ('superadmin', '$HASH', '系统管理员', LAST_INSERT_ID(), 1, '');
INSERT INTO sys_user_role (user_id, role_id, source)
  SELECT u.id, r.id, 'direct' FROM sys_user u, sys_role r
  WHERE u.username = 'superadmin' AND r.level = 0;
COMMIT;
SQL
```

> 建完用**后台登录页**验证一次（不是 SQL 查表）—— 走 API 登录才能在 `sys_login_log`
> 里留下可审计的记录。同一把口令不要同时用在 dev 与 prod。

## 日常更新

```bash
svn update
bash deploy/template.sh prod start      # 全量：迁移 + 构建 + 重载
bash deploy/template.sh prod migrate    # 只跑迁移
bash deploy/template.sh prod web        # 只重建两前端
bash deploy/template.sh prod restart    # 只重启后端（改了代码没改表）
```

`prod start` 步骤与失败策略：

```
[1/6] 检查 server/.env.prod      缺失 → 退出（不静默用默认值）
[2/6] pnpm install --frozen-lockfile
[3/6] NODE_ENV=prod pnpm migration:run   失败 → 中止，不启动新版本
[4/6] pnpm build
[5/6] 同步权限清单 + pm2 startOrReload + 渲染安装两站点 + nginx -t/reload
[6/6] 两前端 pnpm build + rsync 到各自 DEST
```

> **为什么要同步权限清单**：后台角色界面按模块树形勾选，数据源是 `sys_permission`，
> 由 `pnpm authz:sync` 从代码装饰器反射生成。不同步 → 新权限码在界面看不见（**已有鉴权不受影响**）。
> 所以这一步失败只告警、**不阻断启动**。
>
> **为什么迁移必须显式带 `NODE_ENV=prod`**：`data-source.ts` 按 `NODE_ENV` 加载 `.env.$NODE_ENV`，
> 不带就默认 `dev` —— 等于**连开发库跑生产迁移**。

## 停服 / 恢复

```bash
bash deploy/template.sh prod stop           # pm2 stop + 摘两站点软链；产物/配置/库全保留
bash deploy/template.sh prod start          # 秒级恢复
bash deploy/template.sh prod stop --purge   # 彻底清理：pm2 delete + 删产物 + 删站点配置
```

铁律：**绝不 `pm2 kill`、绝不 `systemctl stop nginx`** —— 同机还有其它项目。`stop` 只停本项目。

## 上传大小：三层必须对齐

| 层 | 位置 | 当前值 |
|---|---|---|
| Nginx | `deploy/nginx/*.conf` 的 `client_max_body_size` | **20m** |
| Multer | `server/src/modules/file/file.constants.ts` 的 `MAX_FILE_SIZE` | **10MB** |
| 业务策略 | `server/src/modules/file/file.policy.ts`（只能收紧） | **10MB** |

放宽单文件上限要**三处一起改**，再 `template.sh prod web && template.sh prod restart`。
只改 Nginx → 后端 413；只改代码 → Nginx 直接 413，请求到不了应用层。

## 备份

`backup.sh` 做三件事：全量 dump → `gzip -t` 校验 → 生成同名 `.sha256`；
dump 中途失败会删掉半截文件（一个「看起来存在」的坏备份比没有更危险）。

```bash
# 建议 cron 每日凌晨（密码用环境变量传）
# ⚠ DB_NAME / DB_USER 必须显式写：backup.sh **不再为它们提供默认值**。
#   旧版本默认 DB_NAME=template（dev 库），cron 里漏传就会“每天成功备份开发库”，
#   而生产库根本没有备份 —— 那种事故很安静。
0 2 * * * DB_NAME=template_prod DB_USER=template_prod DB_PASSWORD='<业务密码>' \
          BACKUP_DIR=/data/backups/template \
          /path/to/Template/deploy/backup.sh >> /var/log/template-backup.log 2>&1
```

MinIO 附件**不在 mysqldump 范围内**，需单独备份 `~/Docker/minio/data`（或 `mc mirror`）。
只恢复库不恢复对象 → 附件下载 404（库里 `sys_file` 只是元数据）。

## 恢复演练

`restore.sh` 默认恢复到 **`<项目>_tmp_restore`（固定名）**，每次**先 DROP 再导入**，
**绝不碰生产库**：目标名必须是 `*_tmp` / `*_tmp_restore`，否则直接拒绝（`--force` 才能覆盖）。

```bash
# 校验 + 打印计划（不执行）
bash deploy/restore.sh /data/backups/template/template_prod-20261124-020000.sql.gz --dry-run
# 真演练
bash deploy/restore.sh /data/backups/template/template_prod-20261124-020000.sql.gz --yes
```

顺序：`gzip -t` → 比对 `.sha256` → DROP/CREATE/GRANT 目标库 → **剥掉 dump 里的 `USE` / `CREATE DATABASE`** → 导入 → 打印表数量。

- 目标库固定名，所以**库数量不会随演练次数增长**；上次的表也不会和本次冲突。
- 建库/删库/授权要管理员身份：`MYSQL_ADMIN` → `MYSQL_ROOT_PASSWORD` → 自动发现 mysql 容器（三级回退）。
  一库一账号后业务账号没有 `CREATE DATABASE` 权限，这是有意为之。
- 演练完删掉：`DROP DATABASE template_tmp_restore`（下次演练会重建）。

> **没演练过的备份等于没有备份**：季度至少跑一次恢复，并抽查 `SELECT COUNT(*) FROM sys_user`。

## 常见问题

| 现象 | 原因 |
|---|---|
| 启动报 `Config validation error: JWT_SECRET ...` | 生产密钥 <32 字符 / 仍是模板或 dev 值（**故意拦截**，换随机串即可） |
| `Table 'xxx' doesn't exist` | 没跑迁移，或迁移跑在别的库上（`NODE_ENV` 没带 `prod`） |
| 站点 502 | 后端没起来：`bash deploy/template.sh logs` |
| `nginx -t` 报 `invalid port` | 手拷了带 `__PORT__` 的 conf，应走 `template.sh` |
| 8080 无监听 | 某个 `stop` 摘了站点软链 |
| 登录后提示「无后台访问权限」 | 账号没有 `console:access`（见下） |
| 上传 413 | 三层上限之一超了 |
| 附件 404 但库里有记录 | MinIO 对象丢了（只备份了 MySQL） |
| 发版后页面还是旧的 | 硬刷新；`index.html` 已 `no-store`，通常是浏览器缓存旧 JS |

### 登录后提示「无后台访问权限」

准入码是 `console:access`，超管与校级管理员都有：

| level | 角色 | permissions | 有 `console:access`？ |
|---|---|---|---|
| 0 | 系统管理员 | `*:*:*` | ✅ |
| 1 | 校级管理员 | `*:*:*,!system:*` | ✅（`!system:*` 只排 system 域） |
| 2/3/4 | 部门管理员 / 业务操作员 / 审计员 | 空 | ❌ —— 请去前端 **8084** |

补救（改完让用户重新登录才生效，权限在 JWT 之外的 profile 里）：

```sql
UPDATE sys_role SET permissions = CONCAT(permissions, ',console:access') WHERE id = <角色id>;
```

为什么准入码不叫 `system:console:access`：管理员的 `!system:*` 会挡掉整个 `system:` 域，那样连管理员都进不来；所以它必须落在 system 域之外。
