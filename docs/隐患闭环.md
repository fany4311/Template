# 隐患闭环（示例业务）

> 用一条**真实业务闭环**验证底座是否够用。底座不含业务名词，本模块是「业务侧」样板。
>
> **状态机 / 权限码 / 接口的权威在代码**：`modules/hazard/hazard.state.ts`、`web_admin/openapi.json`。
> 本文件只记设计点与踩点。

## 1. 状态机

```
上报 → REPORTED →(受理) PROCESSING →(提交整改) RECTIFIED →(复查通过) REVIEWED →(归档) ARCHIVED
         │              │                 │
         └── 驳回 ───────┴──── 驳回 ──────┘          复查退回 → PROCESSING
                        ↓
                    REJECTED（终态）
```

- 状态 / 动作 / 流转表 / 权限码**集中在一处**（`hazard.state.ts`），权限码只定义一次。
- 服务层改状态前必须过 `assertTransition()`，非法流转抛 `HazardTransitionError`（`ApiException`，HTTP 200 + 业务码 + 中文原因）。
- `availableActions(status)` 告诉前端「当前能做哪些动作」，**前端不自己判断状态**。
- **审计员只归档、不改内容**（归档是「确认材料齐全」，不是「再修改」），保持审计独立。

## 2. 可见性：四层并集

```
可见 = 角色 dataScope            （底座机制：ALL / 本部门及以下 / 本部门 / 本人）
     OR 我是上报人                （自己报的单永远看得见）
     OR 我部门在协办列表          （多部门协同）
     OR 单据 scope = SCHOOL      （全校通报：所有持有列表权限码的人都能看）
```

第 3 条必须落在 **SQL**（`JSON_CONTAINS`），第 4 条同理（`h.scope = 'SCHOOL'`）；
不能在结果集里过滤，否则分页 `total` 不对。
取不到单据统一返回 **404**（非 403），避免泄漏「这条单据存在但你没权限」。

> 第 4 条的层次：`@RequiresPermissions(hazard:report:list)` 决定「能不能调接口」，
> `scope=SCHOOL` 只决定「能看哪些单」。所以全校通报**不是**「不需要权限」，
> 而是「有列表权限的人都能看到」。同一套规则也被详情与附件鉴权（`canAccess`）复用 ——
> SCHOOL 单的附件同样是全校可见，语义一致。

## 4. 权限为什么两层

| 层 | 机制 | 管什么 |
|---|---|---|
| RBAC | `@RequiresPermissions` + `RbacGuard` | 能不能**进这个接口** |
| CASL | `@CheckPolicies` + `PoliciesGuard` | 能不能对 **Hazard 做这个动作** |

两层过后，服务层再校验**状态机**（这单现在能不能做）与**数据范围**（这单你能不能看）。
三者缺一不可：**能调接口 ≠ 能对这张单做 ≠ 这张单现在能做**。

> 决策 B 后超管是纯 `*:*:*`，**能进业务**（放弃蒙权分离的代价，见 `权限设计-CASL.md` §10）。
> 业务层面的动作边界不靠角色串，而是靠 **CASL 规则**（`@CheckPolicies`）与状态机。

## 5. 一致性：单据 + 轨迹 + 事件同事务

每次流转在**一个事务**里做三件事（`HazardService.flow()`）：改单据字段 → 写 `biz_hazard_log`（时间线）→ `OutboxService.append()` 发领域事件。

六个动作收敛成一个 `flow()` 骨架 —— 状态机、权限码、日志、事件必须同步演进，拆成 6 份必然出现「某个动作忘了发事件」。

> 业务轨迹 `biz_hazard_log`（随单据）≠ 系统审计 `sys_audit_log`（`@Auditable` 自动产生，只读）。

## 6. 省平台对接：先立端口，再换实现

省平台 API 文档未到（对接方「湖南手拉手技术」）→ **先定义端口，用 Mock 实现**，本校侧闭环独立跑通：

```
HazardService ─(事务内)→ sys_outbox → OutboxPublisher → HazardSyncHandler
                                                              │
                                                    ProvinceSyncPort（端口）
                                                              │
                                        MockProvinceAdapter（当前）/ HttpProvinceAdapter（将来）
                                                              │
                                                    biz_hazard_sync（对外同步结果）
```

真接口到位后**只改一行**：`PROVINCE_SYNC_PORT` 的 `useClass`；业务代码、Outbox 处理器、表结构都不动。

两个易踩点：

1. **`biz_hazard_sync` 与 `sys_outbox` 语义不同**：前者记「省平台返回了什么」，后者记「内部事件是否被消费」。投递成功 ≠ 省平台受理成功。
2. **幂等键必须是事件 id，不是 (单据号, 状态)**：Outbox 至少一次投递；用 `(hazardNo, toStatus)` 时，**复查退回**会让单据回到 `PROCESSING`，与受理 `toStatus` 相同 → 被误判重复而**漏推**。现用 `payload.eventId`（唯一索引兜底）。

## 7. 新业务模块接入清单（照抄）

1. `src/modules/<name>/`：`entity / dto(*.dto.ts + *.response.ts) / service / controller / module`。
2. 写操作走 `txHost.withTransaction`；改状态走状态机 `assertTransition`。
3. 每接口 `@ApiOkZod(组件名, schema, 说明)`（否则前端没有响应类型）。
4. 写接口 `@HttpCode(200) + @Auditable + @Idempotent + @RequiresPermissions`。
5. 可见性用 `DataScopeService.resolve()`，跨部门时叠加业务条件（照 `visibility()`）。
6. 迁移拆两条：建表 + (角色授权 + 字典 + 菜单)。
7. 补 e2e：可见性对照 + 状态机非法流转 + 权限两层 + 全流程；响应契约补进 `contract.e2e-spec.ts`。
8. 前端：`api/<name>.ts` + `views/<name>/XxxView.vue`，类型从 codegen 派生，加一条 `sys_menu`。
